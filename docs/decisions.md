# Decisões de arquitetura

As decisões abaixo transcrevem as escolhas da [especificação](./SPEC.md). Mudanças futuras devem ser registradas aqui no mesmo formato.

| ID | Decisão | Motivo | Alternativa descartada |
|---|---|---|---|
| D-01 | Backend 100% Python (FastAPI), sem Node.js. | Centraliza grafos, IA e relatórios no backend existente. | Node.js + Python. |
| D-02 | Métricas em Python puro com NetworkX sobre grafos montados em memória por projeto/janela; interface permite plugar GDS depois. | Grafos de equipe são pequenos, NetworkX é determinístico e fácil de testar. | Neo4j GDS como motor principal. |
| D-03 | Neo4j guarda fatos do grafo; SQLite guarda estado da aplicação. | Jobs, snapshots e relatórios são dados relacionais/documentais. | Guardar tudo no Neo4j. |
| D-04 | LLM local via Ollama, modelo `llama3.1:8b`, acessado por HTTP. | Privacidade e menor número de dependências. | SDK Ollama ou serviço remoto. |
| D-05 | O LLM apenas interpreta métricas e signals determinísticos; números são validados e há fallback por template. | Reduz risco de erros aritméticos e alucinações. | LLM analisando dados brutos. |
| D-06 | O projeto é o tenant; cada projeto pertence a um usuário na v1. | Isolamento simples e seguro. | Grafo global compartilhado. |
| D-07 | Relatórios usam um modelo JSON e renderizadores HTML, DOCX e PDF. | Compatibilidade com Windows e formatos previstos. | WeasyPrint ou Playwright. |
| D-08 | Sem Alembic na v1; usar `Base.metadata.create_all()` e recriar o banco SQLite de desenvolvimento quando o schema mudar. | Menos componentes na versão inicial. | Migrações versionadas. |
| D-09 | Frontend React 19 + Vite + TypeScript + CSS Modules; Cytoscape para o grafo e SVG próprio para linhas. | Mantém a stack existente e evita incompatibilidade com wrappers. | `react-cytoscapejs` e Recharts. |
| D-10 | Jobs usam `ThreadPoolExecutor`, tabela `sync_runs` e agendamento asyncio. | Evita adicionar Celery/Redis ou APScheduler. | Celery/Redis ou APScheduler. |
| D-11 | Persistir apenas metadados; não guardar corpos de commits, PRs ou comentários nem e-mails em claro. | Privacidade/LGPD e minimização de dados. | Persistir texto completo. |
| D-12 | Rótulos dos nós em inglês e tipos de relação em português. | Consistência do modelo do grafo. | — |
| D-13 | Fixar `pytest==9.1.1` e `httpx2==2.13.1` para os testes de API. | O Starlette instalado exige `httpx2` para `TestClient`; verificado no ambiente Python do backend. | `httpx` isolado, que não satisfaz o requisito observado. |
| D-14 | Frontend usa `react-router-dom==7.18.4` e `@tanstack/react-query==5.104.1`; chamadas HTTP passam por `src/api/client.ts`. | Rotas explícitas, cache de sessão e uma política comum de cookies/erros. | `fetch` duplicado em componentes. |
| D-15 | Com `ENV=dev`, `http://localhost:5173` é aceito adicionalmente a `FRONTEND_URL` no CORS e na validação de Origin. Em outros ambientes, apenas `FRONTEND_URL` é aceito. | Permite desenvolvimento local quando `FRONTEND_URL` aponta para o Cloudflare Tunnel sem ampliar a origem confiável fora de dev. | Desativar a validação CSRF ou reescrever Origin no proxy. |
| D-16 | Estado de autenticação e conexões OAuth ficam em SQLite via SQLAlchemy 2.1.4, seguindo o estilo ORM 2.0; `Base.metadata.create_all()` roda no startup e datas são persistidas/retornadas em UTC. | Atende ao modelo relacional da especificação sem migrações na v1; Neo4j permanece reservado aos fatos do grafo. | Guardar usuários e tokens em nós Neo4j. |
| D-17 | Início e callback de conexão OAuth exigem sessão Cognis válida; cada credencial é salva na conexão do usuário autenticado, sem criar usuário a partir de callback anônimo. | Impede conexões órfãs e associa o token ao usuário que iniciou a conexão. | Permitir callback sem sessão e criar usuário implicitamente. |
| D-18 | Trello OAuth guarda access/refresh tokens cifrados, renova quando faltam menos de 5 min para expirar e confirma a rotação dos dois tokens na mesma transação antes de usar o novo access token. Remove `write:board:trello`; mantém `read:member:trello read:board:trello offline_access` conforme o baseline do SPEC. | A referência oficial Atlassian 3LO documenta `offline_access`, refresh tokens rotativos, substituição do refresh anterior, expiração por inatividade de 90 dias e `invalid_grant`. A referência geral não comprova os scopes granulares necessários por endpoint Trello; nenhum scope adicional foi inventado. | Reutilizar refresh token antigo ou manter permissão de escrita desnecessária. |
| D-19 | Fixar `tzdata==2026.5` para resolver fusos IANA via `zoneinfo` em ambientes sem base de fuso do sistema, incluindo Windows. | Permite validar os fusos IANA do projeto de forma consistente no backend multiplataforma. | Aceitar nomes sem validar ou depender de dados de fuso instalados fora do ambiente Python. |
| D-20 | Nas próximas etapas de UI, preservar a identidade visual já desenvolvida pelo usuário; mudanças de layout, paleta e componentes devem partir da interface existente e ser alinhadas antes de uma reformulação ampla. | O trabalho visual do frontend será detalhado em conjunto e não deve ser substituído por uma estética genérica durante a implementação funcional. | Aplicar um redesign independente do estilo atual. |
| D-21 | O coletor GitHub v2 transforma cada review em um nó identificado pelo ID da API, mantém reviews sem usuário sem aresta de autoria, calcula `first_review_at` para reviews enviadas por alguém diferente do autor da PR e persiste somente estado/data. Comentários guardam apenas data e comprimento, nunca o corpo. | A documentação oficial dos endpoints de reviews e comentários confirma `id`, `user` anulável, `state`, `submitted_at`, `pull_request_url` e `issue_url`; a fixture real atual ainda não contém reviews nem comentários inline. | Ignorar reviews/comentários sem amostra, ou persistir corpo textual. |
| D-22 | A visualização do grafo usa `cytoscape==3.34.3` com layout `cytoscape-fcose==2.2.0`; o backend limita a resposta a 400 nós, filtra por projeto e valida a propriedade antes de consultar Neo4j. | Usa as dependências previstas em D-09 sem wrapper React e limita o custo/renderização inicial do grafo. | Duplicar renderer ou retornar o grafo completo sem limite. |
| D-23 | Tela `/p/:pid` em CSS Grid full tela: `GraphTopBar` (56 px) e `GraphToolbar` (48 px) em cima, `LeftDock` (280/56 px) e `RightDock` (340/0 px) nas laterais, canvas na célula central. Docks empurram o canvas e o `cy` é redimensionado com `ResizeObserver` + `cy.resize()`. Peso mínimo da aresta filtra no cliente; sem biblioteca nova. Detalhes em SPEC §12.4.1. | Grafo ocupa o máximo de área sem nós escondidos sob painéis, preserva a identidade visual (D-20) e não adiciona dependências. | Docks flutuando sobre o canvas (esconde nós); `react-resizable-panels`/kit de UI; `min_weight` no servidor a cada movimento do slider. |
| D-24 | Direção visual do grafo “Constelação viva” (SPEC §12.5.1): halos, arestas curvas com gradiente, iniciais em *data URI*, animações com Cytoscape nativo e um controlador `fx.ts`, com níveis `full`/`lite`/`off`. Sem biblioteca nova. | Visual marcante sem trocar a identidade (D-20), com custo controlado e respeito a `prefers-reduced-motion`. | `gsap`/`framer-motion`/`three.js`, renderer WebGL, efeitos sem limite. |

## Histórico

- 2026-10-10: decisões iniciais transcritas da COGNIS_SPEC.md (v1.0).
- 2026-10-10: F1.3 — verificado no [guia oficial OAuth 2.0 3LO da Atlassian](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/) que `offline_access` solicita refresh token; refresh tokens são rotativos, devem ser substituídos, têm validade por inatividade padrão de 90 dias, e `invalid_grant` requer nova autorização. A [referência OAuth REST do Trello](https://developer.atlassian.com/cloud/trello/guides/rest-api/authorization/) descreve os scopes legados `read`/`write`, não a matriz de scopes granulares por endpoint; a verificação granular permanece pendente.
- 2026-10-12: preferência do usuário para as próximas telas: manter como referência a identidade visual já desenvolvida e alinhar mudanças visuais mais amplas antes de reformular.
- 2026-10-14: F2.3 — verificados os esquemas oficiais de [reviews](https://docs.github.com/en/rest/pulls/reviews?apiVersion=2022-11-28#list-reviews-for-a-pull-request), [comentários inline de PR](https://docs.github.com/en/rest/pulls/comments?apiVersion=2022-11-28#list-review-comments-in-a-repository) e [comentários de issue/PR](https://docs.github.com/en/rest/issues/comments?apiVersion=2022-11-28#list-issue-comments-for-a-repository). Corpos são usados somente para extrair comprimento/referências e não são persistidos.
- 2026-10-14: F2.4 — adicionados sync GitHub assíncrono, leitura do grafo e renderer Cytoscape com fCoSE; dependências fixadas em versões exatas.
- 2026-10-13: F4.5 — SPEC v1.1: nova seção §12.4.1 (layout full tela do grafo), ajustes de posição em §12.2, §12.4 e §12.5 e tarefa F4.5 no roadmap. Itens `[VERIFICAR]` pendentes: `dvh` (MDN), Fullscreen API (MDN) e `cy.resize()` (js.cytoscape.org).
